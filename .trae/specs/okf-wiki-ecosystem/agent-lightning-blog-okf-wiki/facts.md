## Rollout 执行流程（F-016 ~ F-022）

| F 编号 | 事实 | 类别 | 核验状态 |
|--------|------|------|---------|
| F-016 | 训练器从 SWE-smith 数据里取出任务，为 Agent 创建一次执行，称为 rollout | 机制 | P1 选核验 |
| F-017 | 控制器启动一个 Kubernetes Job，让 mini-SWE-agent 在对应代码仓库的隔离环境中运行 | 机制 | ✅ 官方核验通过（native Kubernetes support） |
| F-018 | Agent 读任务、查看代码、修改文件、运行命令 | 机制 | P1 选核验 |
| F-019 | 需要模型决定下一步时，请求发往 Agent Lightning 的 OpenAI 兼容 API 代理 | 机制 | ✅ 官方核验通过（LLM endpoint proxy） |
| F-020 | 代理把请求转给训练中的模型，记录 token ID、生成 token 的对数概率，并绑定到对应 rollout | 机制 | P1 选核验 |
| F-021 | 模型给出的动作由 harness 执行；命令报错、文件变化、测试结果等反馈由 harness 整理进下一轮上下文 | 机制 | P1 选核验 |
| F-022 | 训练系统记录的是这套 Agent 实际送给模型的输入，以及模型据此生成的回答 | 机制 | P1 选核验 |

## Rollout 样本拆分（F-030 ~ F-034）

| F 编号 | 事实 | 类别 | 核验状态 |
|--------|------|------|---------|
| F-030 | 真实 harness 会压缩上下文、启动子 Agent、重新拼装模型输入 | 机制 | P1 选核验 |
| F-031 | 同一次 rollout 中，后一个请求未必完整接续前一个，不能总被当成一条不断增长的对话 | 机制 | P1 选核验 |
| F-032 | 即使文本没变，重新套聊天模板、重新分词也可能改变 token 边界 | 机制 | P1 选核验 |
| F-033 | Agent Lightning 默认只在前后调用的 token 确实连续时合并训练序列；接不上就另起一条 | 机制 | P1 选核验 |
| F-034 | 拆分会影响奖励的统计；v1.0 在 rollout 层计算优势，并在损失计算中处理同一 rollout 的整体权重 | 机制 | ✅ 官方核验通过（rollout-level advantage） |

## 同步/异步训练（F-037 ~ F-041）

| F 编号 | 事实 | 类别 | 核验状态 |
|--------|------|------|---------|
| F-037 | 真实 Agent 任务时长很不整齐 | 背景 | P2 可单源 |
| F-038 | 如果同步训练要等整批任务结束，最慢的一组会拖住模型更新 | 背景 | P2 可单源 |
| F-039 | v1.0 的 Collocated Async RL 同时保持更多任务组执行；收齐足够多的完整组就开始一次更新 | 机制名称 | ✅ 官方核验通过 |
| F-040 | 推理和更新共用一组 GPU；更新前网关暂停接收新的模型请求，等处理完再更新权重，更新后恢复 | 机制 | ✅ 官方核验通过 |
| F-041 | 相比同步 RL 带来约 2 倍的端到端加速；共享 GPU 池减少了常规异步方案分别部署推理和训练的资源需求 | 成效数字 | ✅ P0 官方核验通过 |
