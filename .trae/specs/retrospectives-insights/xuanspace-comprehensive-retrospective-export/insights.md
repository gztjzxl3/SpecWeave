# xuanspace（玄境）全面复盘 — I 阶段洞察清单

## 一、洞察清单（四元组）

### I-1 增量节奏从"单峰冲刺"细化为"多段事件脉冲"——协作模型缺少常驻使命

**现象描述**

全量 360 次提交中，2026-08-26 之后的增量仅 38 次，占 10.56%（F-010）。这 38 次并未匀速铺开，而是集中于 8 个活跃日期（F-062）；其中 2026-09-15 + 09-16 两日合计 22 次，09-16 单日即 14 次为增量峰值（F-063）。与之相对，增量覆盖区间内存在四段完全无提交的时段：08-26~09-02、09-05~09-14、09-17~09-20、09-24~10-09（F-064），末段跨度约 15 天。这一形态与全量期高度同构：全量峰值落在 07-31 单日 69 次（F-007），全量活跃日仅 25 天（F-006），且 360 次中 322 次（约 89.4%）发生于 08-25 之前（F-011、F-102）。

**根因分析（5-Whys）**

- Why1：为何增量呈"多段脉冲"而非匀速？因为 38 次提交由若干离散任务事件驱动——xuan-compose 分层重构 14 次、纯 Python 打包双轨化 7 次、子模块同步 6 次、文档原子化与怪癖分级 5 次、文档配置治理 3 次、doctor 子系统 3 次（F-055 ~ F-061），事件内部密集提交、事件之间零提交。
- Why2：为何工作以"任务事件"为单位？因为提交单位绑定到带 Session 标识的 spec 会话——xuan-compose 重构对应 `sc-20260915-podman-compose-refactor`（F-107），上游增量同步对应 `sc-20261010-sync-upstream-delta`（F-110），提交是 spec 执行的交付产物而非日常推进。
- Why3：为何提交绑定 spec 会话？因为第一开发执行主体是 AI Agent（全量 Trae Agent 253 次、xinetzone 107 次，F-012），agent 以"被指派任务→执行→交付"为工作单元，会话结束即进入等待，不具备自主发起能力。
- Why4：为何会话结束即停止、无自发续接？因为协作模型缺少"常驻待办池"——agent 的下一步动作依赖人再次指派，无指派则不产生提交，任务只能以离散会话形式存在。
- Why5（系统性根因）：该节奏是"agent 执行 + spec 会话驱动"协作模型的必然产物——提交粒度被人机交接节奏决定，而非被工程连续性决定。全量期的"阶段冲刺"（一个大 spec 会话）与增量期的"多段脉冲"（多个小 spec 会话）是同构的，差别只是会话的规模与数量。根因不是"缺乏纪律"，而是协作模型缺少 standing backlog：可执行工作没有被登记为可持续消费的队列。

**影响评估**

- 时间：交付节奏不可预测，出现最长约 15 天的空窗（F-064，09-24~10-09），外部难以据此规划依赖；
- 质量：单个事件内部质量高（T9 对等门禁 484 ≥ 478、skip=0、覆盖率 91%，F-113），但事件之间缺少回归接力，前一会话的上下文在空窗期冷却；
- 风险：重复代价显现——上游怪癖"本项目有 10+ 次此类纠正"（F-116）提示同类问题在会话间被反复重新发现。

**改进建议**

1. 建立"常驻待办池 + 定时唤醒"机制：将可独立执行的小任务（doctor 检查扩展、依赖巡检、文档同步、单点版本对齐）登记为 backlog，由定时任务周期性触发 agent 消费，把"等待指派"转为"队列消费"；
2. 为每个 spec 会话在结束报告中强制登记"后继可执行项"，形成会话间任务链，消除事件之间的纯空窗；
3. 将"提交节奏观察"从纯记录升级为"空窗期自动从 backlog 派发"，使节奏观测与节奏修复闭环。

**证据**：F-010、F-062、F-063、F-064、F-055、F-061、F-012、F-107、F-007、F-006、F-011

### I-2 治理重心从"功能扩张"迁移为"结构治理与移植对齐"——"迁入即治理"规律

**现象描述**

全量口径 feat 以 93 次居首（F-013），但增量口径 feat 仅 9 次（23.7%），docs 以 10 次（26.3%）反超为第一大类型（F-014）。更显著的是 build 类：增量中 build 7 条占 18.4%（7/38），而全量中 build 仅 9 条占 2.5%（9/360），占比抬升约 7 倍（F-016）。增量 scope 亦高度收敛于 xuan-compose 系——compose 13 + xuan-compose 7 合计 20/38（F-015）。对照基线 322 条的类型分布（feat 84、test 62、fix 61、docs 48、chore 37、build 2，F-101），增量期的类型结构已发生明显位移。

**根因分析（5-Whys）**

- Why1：为何增量中 feat 不再第一、docs/build 反超？因为增量阶段的主要工作是"把已有上游单体重构进 monorepo 并对其治理"，而非新增功能——xuan-compose 分层重构（F-055）、打包双轨化（F-056）、文档原子化（F-058）占据主体。
- Why2：为何工作是重构/治理而非新增？因为项目已从"从零搭建"转入"整合与对齐"阶段：全量期已完成主干功能（基线 README 所列 COW/Backward/性能优化里程碑），增量期承接的是将 containers/podman-compose 上游迁入并对等（F-107、F-112 对等 v1.6.0）。
- Why3：为何整合阶段集中产生 build/docs 类提交？因为 monorepo 化的成本集中在"结构合规"：20 个 pyproject.toml 需统一构建后端（F-096；F-037~F-044 以 `wheel.cmake=false` 双轨化 7 条）、文档需原子化拆分（F-050 ~ F-052 拆为十文件）、目录命名需规避第三方 `docs/` 约定冲突（F-019 `docs/`→`doc/`）。
- Why4：为何结构合规成本在此窗口一次性释放？因为"整包迁入"会一次性触发该单体此前全部隐性的私有约定——构建后端、目录约定、版本声明、文档形态；这些约束在单一上游项目内部不显性，迁入统一仓库后才暴露为需对齐的公共约束。
- Why5（系统性根因）：这是"迁入即治理"的内在规律——把外部单体纳入统一仓库，会把其私有约定升级为公共约束，治理类提交（build/docs/chore）于是在迁入窗口集中爆发。功能扩张与结构治理在不同成熟度阶段此消彼长，是仓库从"单点开发"跃迁到"平台整合"的表征，而非"产出下降"。

**影响评估**

- 时间：治理提交不直接产出行用户可见功能（增量 feat 仅 9，F-014），短期"功能吞吐"下降；
- 质量：结构统一降低长期多包维护成本（根包 CMake 占位去除、hub package 归零，F-077；20 包构建后端归一，F-096）；
- 风险：治理尚未闭环——`requires-python` 仍有 xuan-compose `>=3.14` 与其余 `>=3.14.6` 的不一致（F-082、F-085），说明一致性复核未覆盖全部 20 个 pyproject。

**改进建议**

1. 把"迁入即治理"固化为检查单：新包迁入时同步执行构建后端对齐（`wheel.cmake=false`）、`requires-python` 与根一致、版本声明单一源、文档原子化，缺一不得合并；
2. 将上述检查纳入 `xs doctor` 自动核验，复用并扩展现有的 doctor 子模块指针/Sphinx 路径检查（F-047、F-048、F-060），使结构一致性可被持续量化；
3. 为"整合阶段"单列验收口径：以"每包构建后端一致率、requires-python 一致率、文档原子化完成率"替代 feat 计数作为阶段健康度指标，避免用功能产出误判阶段成效。

**证据**：F-013、F-014、F-016、F-055、F-107、F-112、F-096、F-037、F-019、F-082、F-101

### I-3 上游依赖策略从"依赖外部"升级为"对外部行为分级建模锁定"

**现象描述**

`libs/xuan-compose/docs/parity/upstream-quirks.md` 建立了上游怪癖固化四级口径——L0（精确断言）/ L1（弱断言）/ L2（注释固化）/ L3（清单固化），并逐条标注级别（F-114）；其中 `create_secrets` 条目由 L1 补全文断言升级为 L0（F-115）；该文档开篇声明"本项目有 10+ 次此类纠正"（F-116）。同期，xuan-compose 将对等目标锁定为 containers/podman-compose v1.6.0（F-112），T9 门禁记录上游 26 个测试文件全量移植、484 ≥ 478、skip=0、覆盖率 91%，T10 记录 142 个上游公开符号 100% 映射（F-113）。依赖面亦为全外部：4 个子模块（tvm-ffi、tvm-book、caffe、mystx）全部为外部仓库且均已初始化、指针无漂移（F-074、F-075）。

**根因分析（5-Whys）**

- Why1：为何需要 L0-L3 分级固化上游怪癖？因为迁移上游时存在大量"非标准但已被依赖"的行为（怪癖），若仅用弱断言，行为漂移不会被察觉。
- Why2：为何会产生"10+ 次纠正"？因为编写测试时按"合理行为"假设，而上游真实行为是怪癖（如报错串第二个片段漏 `f` 前缀，F-115），断言与真实输出冲突需反复回改。
- Why3：为何断言与上游真实行为反复冲突？因为上游怪癖未被任何规约显式记录，只能通过"测试失败→读上游源码→回改断言"的试错链发现。
- Why4：为何不统一用 L0 精确断言、反而要"分级"？因为对全部怪癖都用 L0 会锁死实现细节，上游一改即大面积失败（脆弱性高）；全部弱断言又会漏检。分级是在"检出能力"与"抗上游变更脆弱性"之间按怪癖稳定性做的显式权衡。
- Why5（系统性根因）：该策略把"依赖外部代码"升级为"对外部行为建模并分级锁定"——面对不可控外部依赖，通过在本地建立"行为契约台账 + 分级断言"把外部不确定性内部化；L0/L1 是"可验证的强契约"，L2/L3 是"低成本的弱记录"，二者按稳定性分工。这是对"外部依赖不可控"这一系统性约束的机制性回应，可迁移到任何 fork / vendor / 对等重构场景。

**影响评估**

- 质量：对等性可量化验证（484 ≥ 478、skip=0、142 符号 100% 映射、覆盖率 91%，F-113），迁移风险显著收敛；
- 风险：怪癖台账使上游升级时能快速定位受影响断言——紧随其后的上游增量同步（e3df104 → 1f1cb09，11 个非合并提交，F-110）即以该台账为比对基底；
- 复杂度：分级增加了断言的维护心智成本（需判断每条怪癖的稳定性级别），但换取了脆弱性可控与可审计。

**改进建议**

1. 将 L0-L3 分级从单文件约定（F-114）上升为仓库级规范，写入 xuanspace 的 AGENTS.md / 构建规范，使新迁入包默认遵循；
2. 对上游同步类 spec（如 F-110）强制增设"怪癖台账 diff 复核"验收门：同步后须逐条判定台账条目的新增/升级/失效；
3. 将"怪癖发现→回改断言→登记级别"的试错链沉淀为可复用的"对等重构检查单"，降低后续迁移的"10+ 次纠正"重复成本。

**证据**：F-114、F-115、F-116、F-113、F-112、F-074、F-075、F-110

### I-4 结构由"单包极化"迁移为"多库扩张"，与全局一致性债并存

**现象描述**

`libs/` 现为 8 个条目（caffe-ffi、demo-ffi、mystx、npu-ffi、tvm-book、xuan-compose、xuan-core、xuan-ext-demo，其中 mystx/tvm-book 为子模块，F-090），较基线所述 6 个子项目（里程碑报告 F11）新增 xuan-compose 与 mystx；`apps/` 仍仅为 `.gitkeep` 与 README（F-089），`attic/` 亦为空壳（F-093）。子模块面发生实质变化：由基线"3 个子模块均未初始化"（基线 F-014）变为"4 个子模块全部初始化且指针无漂移"（F-075、F-074），与增量期 6 次子模块同步（F-057）一致。同时一致性债仍在：xuan-compose `requires-python >=3.14` 与其余库的 `>=3.14.6` 不一致（F-082、F-085）；工作区在采集时点记 13 行未提交改动（F-070），复核时点记 20 行（19 ` M` + 1 `??`，F-128）。

**根因分析（5-Whys）**

- Why1：为何结构重心从"单包极化"转向"多库扩张"？因为增量期迁入 xuan-compose（F-024 起）并新增 mystx 子模块，`libs/` 由 6 增至 8（F-090），新增了完整的第二方库。
- Why2：为何新增库的同时 `apps/` 仍为空壳？因为项目定位为"库 monorepo"——PDM workspace 仅声明 apps/libs/tools 三来源（F-127），apps 作为预留容量尚未被填充（F-089）。
- Why3：为何子模块从"未初始化"变为"全部初始化"？因为增量期持续执行上游同步（F-057 共 6 次：新增 mystx、URL 转 SSH、多次指针前进、tvm-ffi 结构同步），子模块由"备而不用"转为"实际依赖"。
- Why4：为何结构扩张的同时仍残留一致性债？因为结构变更由多个独立会话分散完成（xuan-compose 迁入、mystx 新增、子模块同步分属不同 spec），缺少"结构变更后的全局一致性复核"环节。
- Why5（系统性根因）：monorepo 的"结构扩张"与"全局一致性"由不同机制驱动——扩张是局部会话事件（增量、去中心化），一致性需全局视图（集中、需统一扫描）。当扩张速度快于全局复核频率时，一致性债（版本声明、工作区清洁度、构建后端）必然累积。这是"分布式增量变更 vs 集中式全局约束"的结构性张力，而非某次疏忽。

**影响评估**

- 质量：第二方库落地提升复用面，xuan-compose 自带 53 个测试文件（F-118），libs 测试总量可观；
- 风险：版本声明不一致（F-082）与持续 in-flight 的工作区（F-070、F-128）使"仓库当前状态"不能作为确定性依赖，任何以工作区快照为输入的结论都需标注时点；
- 复杂度：20 个 pyproject.toml（F-096）放大了一致性维护面，单点漂移的排查成本随包数线性上升。

**改进建议**

1. 引入"结构变更后全局复核"节点：每次新增/迁入库后统一运行一致性检查（`requires-python`、构建后端、版本声明、文档形态），产出可归档的复核报告；
2. 将 in-flight 工作区视为常态而非异常：凡报告涉及工作区事实，一律双时点标注（本复盘已在 F-070 与 F-128 落实），并明确规定"工作区快照不得作为确定性结论的唯一依据"；
3. 为"空壳目录"（apps、attic，F-089、F-093）明确"预留 / 孵化 / 归档"状态标注，消除"存在即开发中"的模糊语义。

**证据**：F-090、F-089、F-075、F-082、F-085、F-070、F-128、F-096、F-118、F-057、F-127、F-024
