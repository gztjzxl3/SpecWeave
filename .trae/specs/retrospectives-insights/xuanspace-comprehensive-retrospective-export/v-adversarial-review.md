# xuanspace（玄境）全面复盘 — V 阶段对抗审查记录

> 审查对象：`insights.md`（I-1 ~ I-4）与 `e-stage-pattern.md`（候选 A/B 去重裁决与模式 B 萃取）
> 审查视角：魔鬼代言人 / 新人 / 老板 / 未来（四视角全覆盖）
> 独立性声明：本文件不复述 I/E 已有结论，仅提交可被反驳的质疑；每条标注视角、针对对象与严重度。

## 一、意见清单（V-1 ~ V-7）

### V-1

- **视角**：魔鬼代言人
- **针对对象**：`e-stage-pattern.md` §2.1 候选 A 裁决（并入 `behavior-characterization-freeze`）
- **意见正文**：裁决本身正确，但存在**反向风险未被论证**：判"并入"意味着既有文档要承载本复盘的差异点，若并入内容无边界，`behavior-characterization-freeze.md` 会从一篇机制模式膨胀为"怪癖台账操作手册 + 仓库级规范建议 + 同步门禁"的大杂烩，反而降低其可读性与可迁移性。质疑点：并入的**上限**在哪里？"不新建"结论是否掩盖了"本可新建但为避免重复而妥协"的真实代价？
- **严重度**：中

### V-2

- **视角**：新人视角
- **针对对象**：`e-stage-pattern.md` §1.2 模式 B 核心步骤
- **意见正文**：初稿步骤 2 直接写入 `wheel.cmake=false`、`>=3.14.6` 等 xuanspace 专有值。新人既不懂这些值，也会误把模式当"xuanspace 操作手册"照抄，导致模式**不可迁移**（回到 I-3 自评所指的"单案例抽象过度"风险）。术语与谓词必须先通用化，案例值降为证据挂 F 编号。
- **严重度**：中

### V-3

- **视角**：老板视角
- **针对对象**：`e-stage-pattern.md` §1.4 迁移验证 + `insights.md` I-2 建议（纳入 doctor 自动核验）
- **意见正文**：模式要求"纳入自动核验"，但**未给 ROI 边界**。若某次迁入只涉及 1~2 个包且此后不再迁入，为它写自动核验脚本的一次性成本可能高于"人肉对齐一次"的成本；治理投入应在超过阈值时才成立。质疑点：本模式是否可能被用于推销"为小规模一次性场景上重治理"，从而制造 ROI 为负的治理？
- **严重度**：中

### V-4

- **视角**：未来视角
- **针对对象**：`e-stage-pattern.md` §1.2 步骤 3（纳入自动核验）/ 模式 B 存续性
- **意见正文**：1 年后若包管理器（如 PDM workspace）或构建后端（scikit-build-core）原生提供"多包约定一致性校验"，本模式的第 3 步将被工具替代，模式是否随之被淘汰？质疑其是否只是"工具缺位期的过渡形态"。
- **严重度**：低

### V-5

- **视角**：魔鬼代言人（**指向事实证据强度不足**）
- **针对对象**：`facts.md` F-113（T9/T10 自报值）、`insights.md` I-3 影响评估、`e-stage-pattern.md` §1.4
- **意见正文**：I-3 与 E 阶段以"484 ≥ 478、skip=0、覆盖率 91%、142 符号 100% 映射"论证"迁移风险显著收敛"，但 F-113 全部来自 xuan-compose `CHANGELOG.md` 的**项目自述**，本任务**未重跑**任何构建或测试（spec.md Non-Goals 亦明确不重跑）。以未经验证的自报数据支撑结论，属**证据强度不足**；若自报值失真，模式 B 的"迁移完成度佐证"即失去依据。
- **严重度**：高

### V-6

- **视角**：魔鬼代言人
- **针对对象**：`insights.md` I-1（增量"多段脉冲"根因＝缺少 standing backlog）
- **意见正文**：I-1 把节奏归因于"协作模型缺少常驻待办池"，但存在**更简解释**：项目已进入维护/整合期，可执行工作量本身下降，"提交少"未必源于协作机制缺陷，而可能只是"该做的做完了"。若如此，"建立常驻待办池"的改进建议可能解决一个并不存在的问题。质疑点：I-1 的 5-Whys 是否把"现象"（提交少）过度上升为"系统性根因"（协作模型缺陷）？
- **严重度**：中

### V-7

- **视角**：新人视角
- **针对对象**：`e-stage-pattern.md` §1.1 触发场景（模式 B）
- **意见正文**：触发场景把"外部单体整包"与"新第一方包"并列，但两者对齐对象并不相同（前者需对上游怪癖与许可隔离额外处理，后者无上游），新人难以据此判断自己属于哪一类、是否该启用本模式；建议拆分为两个子场景或明确统一判定条件。
- **严重度**：低

## 二、采纳与修正痕迹（逐条对照）

> 判定口径：采纳须有可核验的**修正痕迹**（改动 `e-stage-pattern.md` 的具体位置，或明确记录为报告限定说明）。本阶段**不修改** `insights.md`、不写入 `projects/xuanspace`。

### V-1 → 采纳

- **采纳 → 修正了什么**：改动 `e-stage-pattern.md` **§2.1**——将"并入要点"加上边界约束"**严格限于 3 条**"，并把并入内容重组为 3 条编号差异点（①台账载体与同步复核门禁；②分级上升为仓库级规范的建议；③上游同步 spec 须输出台账 diff 复核结论）；同时在"不新建的理由"中补明"差异点总量可用 3 条以内补充表达，不足以独立成篇"。**未新建**候选 A 的独立 L1 文档。
- **修正效果**：回应了"并入无上限"的质疑——用 3 条硬上限锁死增量规模，避免既有文档膨胀。

### V-2 → 采纳

- **采纳 → 修正了什么**：改动 `e-stage-pattern.md` **§1.2 步骤 2**——由写入专有值（`wheel.cmake=false`、`>=3.14.6`）改为**通用动作表述**（对齐构建后端与构建参数声明 / 对齐语言版本约束 / 统一版本声明单一源 / 对齐目录与文档形态），并就地标注"xuanspace 专有值仅作案例证据，见 §1.5"。
- **修正效果**：模式正文与案例证据解耦，消除"照抄成操作手册"的可迁移性风险。

### V-3 → 采纳

- **采纳 → 修正了什么**：改动 `e-stage-pattern.md` **§1.4**——新增"**可判定成功信号 4（成本边界）**"：模式收益以"一次性对齐成本 vs 漂移复发成本"核对，当包数 ≥N 或迁移频率高时自动核验收益为正，小规模一次性迁入可退化为人工检查单。
- **修正效果**：为"是否值得投入自动核验"给出阈值判据，防止把重治理套用到 ROI 为负的小场景。

### V-5 → 采纳（证据强度）

- **采纳 → 修正了什么**：改动 `e-stage-pattern.md` **§1.4**——将原"补充证据"条目改写为"**补充证据与口径限定**"，显式标注 F-113 的 484 ≥ 478、91%、142 符号均为 CHANGELOG **项目自报口径、未经本任务重跑验证**，仅作规模量级参考；并新增自律条款"一致性判定须以仓库文件实体（各 `pyproject.toml` 实读，如 F-082、F-096）为准，不得以自报值充当一致性证据"。
- **修正效果**：把"自称达标"降级为参考值，切断"结论建立在未验证自报值之上"的论证链。

### V-6 → 采纳（记录为报告限定说明）

- **采纳 → 修正了什么**：新增 `e-stage-pattern.md` **§4.1 "上游洞察限定"**——明确 I-1 的系统性根因应表述为"与现有事实一致的一种解释"，并显式标注竞争假设（维护期工作量下降）与证据缺口（`facts.md` 未采集"可执行工作量"类事实）。因 E 阶段不得改写 I 阶段结论，该限定**以"报告限定说明"形式带入 Task 4 报告**，不改写 `insights.md`。
- **修正效果**：把 I-1 的强断言（"必然产物"）降级为可反驳的解释，并据实暴露证据缺口。

## 三、不采纳意见与理由

### V-4 → 不采纳

- **不采纳理由**：本模式的价值锚在**流程性检查单**（"迁入窗口内一次性对齐私有约定 + 单列验收口径"）与**判定纪律**（未解释偏离数、字段级证据），而非"某个具体核验脚本"。工具若原生提供一致性校验，只会**降低模式第 3 步的执行成本**，不会取消"识别隐性私有约定→同一窗口对齐→单列验收口径"的流程判断。因此不因工具演进判其淘汰；仅需在模式"失效条件与演进"中登记"工具原生支持可降级为工具配置"（Task 5 实施时补），当前不删改模式步骤。

### V-7 → 不采纳

- **不采纳理由**：触发场景已通过"适用于 / 不适用于"两栏界定（§1.1）：两类迁入共享的判定条件是"迁入是否**一次性暴露**被迁包的隐性私有约定"，差异项（上游怪癖、许可隔离）由 §1.3 反模式第 4 条与执行时"有意偏离登记"覆盖，无需拆分为两个子场景——拆分反而稀释模式主机制。故维持单场景表述。
