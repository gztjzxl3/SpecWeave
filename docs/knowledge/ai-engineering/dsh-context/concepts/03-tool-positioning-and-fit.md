# dsh-context 的定位、适用场景与可迁移方法论

## 容易误读的地方

README 里用到 `management`（上下文管理）字样，但从目前公开文档看，dsh-context 的主要能力是**观测、定位和回看**[F-028](../references/facts.md)。它：

- **不会主动删上下文**；
- **不会替你决定什么时候压缩**；
- **不改模型、也不负责帮你省 token**（发布者观点 [F-031](../references/facts.md)）。

真想省上下文，还是得从**工具数量、提示词、注入内容和任务拆分**下手[F-029](../references/facts.md)（发布者观点）。

## 适合哪些情况

- **偶尔用 DSH 聊几句**：装不装这个插件差别不大。
- **长会话、多工具、多插件、多 Agent**：它能提供的信息会多一些[F-030](../references/facts.md)。
- **把它当排查工具用**：它只负责把上下文组成、变化过程、文件操作和 Agent 关系**摊开**，怎么处理还得看项目。真出问题时，**至少有明细可查**[F-031](../references/facts.md)。

## 从 dsh-context 提炼的可迁移方法论

以下为原创提炼（来自见解 M-1/M-2/M-3），可迁移到其他含大量隐式上下文的系统（Agent、IDE、重上下文 CLI）：

| # | 可迁移实践 | 落地到其他系统 |
|---|-----------|---------------|
| T-1 | **可观测优先，优化其次**——先提供"上下文构成 + 变化事件"可视化，再谈节流 | 任何上下文密集工具先做上下文构成面板 |
| T-2 | **多入口共享同一事实源**——所有查看入口统一读官方 token-meter 投影，避免数字打架 | 多面板 UI 共用同一底层数据源 |
| T-3 | **给工具标来源**——工具 schema 标注 first-party / capability / mcp / plugin | 降低"谁塞进来这么多上下文"的排查成本 |
| T-4 | **估算与精确分开展示**——估算值标注口径，精确值由 provider 侧提供 | UI 上区分"估算"与"实测"，防止误把近似当精确 |

配套的三个核心洞察（四元组见 [knowledge-map.md](../references/knowledge-map.md)）：

1. **观测先行，优化后置**：没有可取证的观测，省 token 只能靠猜；default 假设"上下文不够 = 输入太多"常被工具 schema 占大头的事实推翻。
2. **多入口是同一事实源的分发**：不是功能叠加，是按查看时机切分。
3. **估算值有边界，精确值才可引用**：引用 token 数据时优先 provider 上报侧。

## 要不要装：三问速判

| 问题 | 是 → 值得装 | 否 → 可不装 |
|------|------------|------------|
| 是否常跑长会话 / 多工具 / 多插件？ | 装的收益更明显[F-030](../references/facts.md) | 偶尔聊聊差别不大 |
| 是否曾因压缩后找不到"到底哪块占了"而困扰？ | 装，它提供明细 | 未困扰可不装 |
| 是否想省 token？ | **错位期望**——它不省 token，只让省 token 决策可取证 | 应转向管工具/提示词/注入/任务拆分[F-029](../references/facts.md) |

## 未来视角：这是过渡形态吗

dsh-context 解决的是"上下文构成不透明"的观测痛点。这类能力**未来很可能被 DSH 官方原生内置**（正如 token meter 已进入内核[F-039](../references/facts.md)）。因此把它当作**当下的排查/观测手段**，而非长期依赖的架构组件，较为稳妥——一旦官方直调后端的观测工具出现，一次方插件的"估算误差"会被原生方案取代（见解 M-3）。

## 一句话结论

> dsh-context 提供的不是省 token 的魔法，而是**让"能不能省、省哪里"变得可取证**。它把上下文组成的黑箱摊开，具体怎么治理由你决定。
