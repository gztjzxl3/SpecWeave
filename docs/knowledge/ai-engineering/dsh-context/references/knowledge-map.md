# dsh-context 知识地图（Knowledge Map）

> 采集协议：wechat-public-okf 的 I 阶段。三层结构：Fact（事实）/ Mechanism（机制/执行者洞察）/ Transfer（可迁移、中立实践）。执行者洞察一律与事实、作者观点分层；基于单源的机制洞察标注 hypothesis。

## 三层结构

### 1. Fact 层（事实映射）

- dsh-context 是 DSH 开源插件，用于可视化上下文生命周期（F-001、F-002）。
- 四类查看入口（F-004/F-035）、跨会话 Insights（F-005/F-006/F-037）、单会话 Context 标签页（F-008/F-038）。
- 当前窗口组成（F-010）、趋势（F-013/F-014）、浏览器（F-015~F-018）、文件活动（F-019）、Agent 网络（F-020）。
- 安装与更新命令（F-021~F-024）、开源地址与仓库体量（F-032/F-033）。
- 兼容矩阵与 Node 要求（F-025/F-026，见 verification 时效口径）。

### 2. Mechanism 层（机制洞察 · hypothesis）

以下为执行者在单信源基础上归纳的工作机制假设，非文章原文，须标注 hypothesis，多信源尚未验证：

- **见解 M-1（hypothesis）**：dsh-context 的核心价值是"把黑箱的 token 占用摊开成可审计的结构化视图"——它是**观测层**插件，改动的是"看上下文的方式"，不触碰模型的推理路径。证据：F-012（估算用 DSH 固定密度启发式）、F-031（作者定位为排查工具）、F-039（占用率复用官方 token meter 投影）。反常识：多数"省 token"方案是改输入（提示词/任务拆分），而 dsh-context 走"先看清再下手"路线，它不省 token，只让省 token 的决策可取证。
- **见解 M-2（hypothesis）**：多入口设计（page/tab/panel/command）本质是按"查看时机"做产品分层——跨会话复盘用 Insights、会话内深查用 Tab、聊到一半随手看用 `/context`。反常识：入口多不是功能冗余，而是掩盖"同一份数据在不同居留场景的唯一事实源"问题（F-009/F-039 都复用官方投影数据，保证多入口数字一致）。
- **见解 M-3（hypothesis）**：默认数值是"估算 + 何时开始发生压缩/剪枝"的定位半衰期展示，精确值需 provider 上报。反常识：上下文占用天然是概率性估值（F-012/F-018 多次"近似/估算"），把它当精确测量使用是误用。

### 3. Transfer 层（可迁移的中立实践 · 尊重边界与同意）

以下为本包提炼的可复用实践，与具体插件解耦：

- **T-1**：任何含大量隐式上下文的系统（Agent、IDE、重上下文 CLI），优先提供"上下文构成 + 变化事件"可视化，再谈节流——**可观测优先，优化其次**。
- **T-2**：多入口 UI 共享同一份底层投影数据（同一事实源），避免各页面数字打架。
- **T-3**：工具繁多时给工具 schema 标来源（first-party / capability / mcp / plugin），降低"谁塞进来这么多上下文"的排查成本。
- **T-4**：把"估算值"与"provider 精确值"在 UI 上分开展示，并明确标注估算口径，防止用户把近似当精确。

## 四元组洞察（I 阶段核心产出 · 供 concepts 采纳）

### 洞察 I-1：观测先行，优化后置
- **陈述**：上下文治理应先建立可取证的观测，再谈压缩或省 token；缺少观测的"省 token"只能靠猜。
- **证据**：F-010、F-015、F-031（插件负责摊开组成与变化，处理交给项目）。
- **反常识**：普遍默认"上下文不够用 = 我输入太多"，实际常是工具 schema 与工具结果占大头（F-011）。
- **行动**：在 DSH 长会话场景安装 dsh-context，用 Current Context 定位占用大头，再针对性削减工具/提示词/注入。

### 洞察 I-2：多入口是同一事实源的分发，不是功能叠加
- **陈述**：page/tab/panel/command 四个入口共享同一份官方 token-meter 投影，只是"居留场景"不同。
- **证据**：F-009、F-035、F-039。
- **反常识**：功能看似重复，实为按查看时机切分；多入口相一致的根因是共享数据源。
- **行动**：排查时按场景选入口，不要在 Insights 页翻单会话明细；理解共享数据后不需跨页对账。

### 洞察 I-3：估算值要有边界，精确值才可引用
- **陈述**：dsh-context 的组成分类数字多为 DSH 固定密度启发式估算，精确值须 provider 上报。
- **证据**：F-012、F-018、F-042。
- **反常识**：界面数字看似精准，实为估算；钉住某步才出现实际 prompt/output/cache。
- **行动**：引用 token 数据时优先用 provider 上报侧；需要精确只能等官方直调后台，任何一次方都有细微差别。

> **可复现性二问**（决定是否建 examples/）：① 有无确定的输入/过程/可观测输出？——安装命令确定、界面可观测；② 独立执行者能否复现？——能按 README 复现安装与界面。**两问皆 yes → 可行 examples/。** 但本包制作中未真机安装（见 verification），examples 仅登记命令与判据，不伪造实测截图。
