# 迁移窗口的结构约定对齐法（迁入即治理）

## 模式类型

方法论模式 → 治理策略（外部单体或新包迁入统一仓库时的结构一致性治理）

## 成熟度

L1（单案例：xuan-compose 迁入统一仓库并完成纯 Python 打包后端双轨化，2026-09-16）。
同一案例内存在多次独立应用形态——外部单体整包迁入、新第一方包接入、构建后端归一扫描，
但按多案例原则，跨项目验证缺失前标 L1。

## 一句话

把外部单体或新包迁入统一仓库时，"私有约定暴露"与"公共约束对齐"必须在**同一迁移窗口内**
一次完成，并以自动核验把一致性从"人肉复核"升级为"可量化复现"。

## 适用场景

**适用于：**

- 将第三方/上游单体整包、或新第一方包，迁入一个**已存在公共约定**的统一仓库（monorepo），
  公共约定至少覆盖：构建后端与构建参数、语言版本约束、版本声明来源、目录与文档形态；
- 迁入动作会**一次性暴露**被迁包内部此前"隐性、不显式"的私有约定——这些约定在单包内部不构成
  问题，进入统一仓库后才成为需对齐的公共约束；
- 需要把对齐结果**可复核地固化**（人工检查单 + 自动核验）。

**不适用于：**

- 迁入目标为独立新仓库——无公共约定可比对；
- 单文件或少量函数搬迁——不存在结构性约定需要对齐；
- 迁入方**有意保留差异**（如许可隔离、独立发布节奏、上游强制目录约定）——此类差异应显式登记为
  "有意偏离"，而非强行拉平。

## 问题背景

单体或第三方包在自有仓库内长期演化，会积累大量未显式声明的私有约定：构建后端怎么选、
构建参数怎么传、语言版本约束写多少、版本号从哪里来、文档放哪个目录。这些约定在单包内自洽，
一旦迁入已存在公共约定的统一仓库，就会在公共面上暴露为漂移——同一仓库同时存在两套构建口径、
两套版本约束、两套目录形态。漂移的排查成本随包数线性上升，而"对齐留在以后统一"会让治理债
随每一批迁入持续累积。若对齐只靠人肉复核，结论随人走、不可复现、无回归。本模式把对齐动作
锁进**迁移窗口本身**，并把可机械判定的部分交给自动核验。

## 核心做法（5 步）

1. **盘点公共约定基线**：从仓库根与既有同类包提取"公共约定集"，逐项列明判定方式。
2. **迁移即对齐**：在迁入提交/切片内**同步完成**每一项对齐，不遗留到"以后统一"——即对齐构建后端
   与构建参数声明、对齐语言版本约束、统一版本声明单一源、对齐目录与文档形态。
3. **纳入自动核验**：把可机械判定的约定做成检查项，接入 `doctor`/CI，使一致性可量化、可复现、
   可回归（具体值域与脚本形态属实现细节，见「案例证据」）。
4. **迁移窗口单列验收口径**：以"每包约定一致率 / 未解释偏离数"替代功能提交计数，作为该阶段的
   健康度指标。
5. **关闭窗口前全局复核**：迁入完成后运行一次全量一致性扫描，产出可归档的复核报告。

## 反模式（均来自实际教训）

- ❌ **只迁不改**：把上游整包原样放入公共仓库，隐性私有约定进入公共面。
- ❌ **对齐留在"以后统一"**：治理债随包数累积，单点漂移的排查成本随包数线性上升。
- ❌ **对齐仅靠人肉复核、无自动核验**：一致性结论随人走、不可复现、无回归。
- ❌ **把"有意偏离"当缺陷强行拉平**：破坏许可隔离、独立发布等设计意图。
- ❌ **用功能产出度量迁移期成效**：以 feat 计数替代结构一致性指标，误判阶段价值。

## 检验标准

- **可判定成功信号 1**：迁入完成后全仓一致性扫描中"未解释偏离数 = 0"，或每一偏离均有登记条目
  与理由；
- **可判定成功信号 2**：自动核验脚本可在**不检出上游**的环境独立运行，对每一项约定输出
  "包 → 项 → 期望 vs 实际"的字段级结论；
- **可判定成功信号 3**：检查单的每一项在目标包中可被逐条核对，且该检查单可被下一个迁入包
  直接复用；
- **可判定成功信号 4（成本边界）**：模式收益以"一次性对齐成本 vs 漂移复发成本"核对——当包数
  ≥ 阈值或迁移发生频率高时，自动核验的收益为正；小规模一次性迁入可退化为人工检查单，不必强上
  自动核验。

> **口径限定（证据强度）**：源案例中门禁相关自报值——"484 ≥ 478、skip = 0、覆盖率 91%、
> 142 符号 100% 映射"——均来自项目 `CHANGELOG.md` 的**项目自报口径，未经独立重跑验证**，
> 仅作迁移完成度的规模量级参考。一致性判定须以**仓库文件实体**（各 `pyproject.toml` 实读）
> 为准，不得以自报值充当一致性证据。

## 迁移示例

- **组织/职能整合**：两个团队合并进统一工程体系时，在同一整合窗口内对齐代码规范、构建口径、
  版本发布口径与文档形态，并将可机械判定项纳入统一检查（CI/门禁）。
- **数据仓库多源接入**：多个上游数据集接入统一数仓时，在同一接入窗口内对齐分区命名、字段类型
  口径、时间粒度与元数据登记。
- **前端多包仓库引入新组件库**：组件库迁入 monorepo 时，在同一窗口内对齐构建配置、TypeScript
  版本约束、包版本来源与文档形态。
- **待验证方向**：制度文本并入统一标准体系、多来源数据字典合并。

## 案例证据（xuanspace）

- 迁移窗口触发：xuan-compose 迁入统一仓库；纯 Python 打包后端双轨化；20 个 `pyproject.toml`
  构建后端归一扫描。
- 一致性债残存（反例）：`requires-python` 未在同一窗口内闭环，出现 `>=3.14` 与 `>=3.14.6` 并存
  ——说明"对齐留到以后"会实际留债。
- 目录约定对齐：`docs/` → `doc/` 以规避第三方路径约定冲突。
- 自动核验雏形：`doctor` 子模块指针检查与 Sphinx 路径检查。
- 文档形态对齐：对等文档原子化为十文件。

## 失效条件与演进

- **当包管理器或构建后端原生提供多包约定一致性校验时**，本模式第 3 步（纳入自动核验）可**降级为
  工具配置**，但模式价值锚仍在流程判断（识别隐性私有约定 → 同一窗口对齐 → 单列验收口径），
  不因工具演进被淘汰；
- 公共约定基线本身发生变更（如切换构建后端标准）时，已对齐包需重新扫描，检查单需同步修订；
- 出现跨项目验证案例后可升 L2。
