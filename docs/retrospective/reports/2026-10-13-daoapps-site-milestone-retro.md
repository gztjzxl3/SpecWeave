# daoApps 组织站点里程碑复盘（projects/daoapps.github.io）

## 执行摘要

daoapps.github.io 是 daoApps 组织的公开站点（GitHub Pages），承载组织主页（14 仓库 / 5 类用法）、`/jieban/` 结伴子站（四频道 + 公约 + 缘起）与 `/fupan/` 复盘子站。仓库自 2026-09-18 首提交至 2026-10-07 共 12 个提交，经历了「手写 HTML → 产物入库 → 全站 Sphinx 源码托管重构 → 契约测试体系 → 复盘子站上线」的完整演化。本次以七概念方法论（R→I→E→V→A→C，standard 深度）执行里程碑复盘。

核心结论：本仓库最有价值的治理决策是**把内容纪律从「人记得」转成「构建卡住」**——引文版本身份证、内部群昵称禁用、无表单承诺、页脚合规分层全部由构建期守卫与 31 项契约测试机器守护；唯一显式不自动化的纪律（禁止笼统称帛书本）经过误伤分析后以文字条款承载。V 阶段对抗审查抓出复盘自身的一处事实错误（测试计数未实测）与一处过度断言（「唯一不机器化」），已全部修正。

## 2. 核心洞察（I 阶段，四元组）

> G2 质量门：每条含 陈述 / 证据(Fxx) / 反常识点 / 下次行动。V 阶段修正已并入（I1 断言收窄）。

### I1 · 内容纪律的机器化分流，边界是「可判定性」而非「重要性」

- **陈述**：本仓库的内容纪律几乎全部机器守护——引文版本（F12–F13）、内部群昵称（F33）、无表单无弹窗（F34）、页脚合规分层（F15）、仓库清单计数（F16）；唯一被显式登记为不自动化的纪律是「禁止笼统称帛书本」（F14），理由不是它不重要，而是公约页自身要引用该规则、机械匹配必然误伤。分流的取舍标准是「机器能否无歧义判定」，不是纪律的重要性等级。V3 修正：并非所有纪律都已机器化——「组织主页规则限定 `.org-home` 内、不外溢结伴站」（F24）至今无机器断言，属尚未分流而非主动豁免。
- **证据**：F12, F13, F14, F15, F24, F33, F34
- **反常识点**：直觉上越重要的纪律越该自动化；本仓恰恰相反，最重要的古籍引文纪律之一主动放弃自动化。自动化的恰当边界是判定能力，不是重要性。
- **下次行动**：新增纪律先过「可判定性测试」——能写出无误伤断言的进 conf.py/tests；不能的进 covenant.md 文字条款，并在 AGENTS.md 登记取舍理由；同时为 `.org-home` 外溢补机器断言（→ ACT-3）。

### I2 · 第二次为同一错误付费时立即根治，不当月结

- **陈述**：09-18 一天 9.5 小时内完成「手写 HTML → 产物入库 → 两次产物修复 → 全站源码托管重构」全循环（F42）。产物入库期间，一次文案修正要同步改源码与产物两处、产物全量重生成 ±6975 行（F41、F05）；重构后所有 fix 只改 `doc/` 源码且各带测试增量（F08）。根治发生在第二次为产物买单的当天，不是月底。V4 修正：根治是消除根因，不是拆除出错环节——词干器守卫误报（F09）的根治方式是收窄断言，守卫保留。
- **证据**：F03–F08, F09, F41, F42
- **反常识点**：重构通常被排在「问题积累够多」之后；本案在债务出现的同一天清偿。止损的最佳时点是第二次为同一错误付费时，而非第 N 次。
- **下次行动**：任何「先凑合上线」的临时方案登记付费次数；第二次付费当天触发根治评审，根治方案以「消除根因」为验收标准（废除、收窄、替换均可），不以「恢复原状」为标准。

### I3 · 修复即测试增量，但承载纪律的元信息自身无守护

- **陈述**：重构后 4 个 fix 提交（含 f7726e0）每个都同步扩充契约测试（测试文件 +82/+59/+44/+75 行）；测试注释承载事故史（F26、F27、F28），断言守护根因（token 语义）而非现象（kbd 黑块）。31 个测试守护 8 类纪律（F16）。但测试文件 docstring 写「校验五件事」与实际 8 类不符（F17），区域路由文件写「22 项」与实测 31 不符——活文档的元信息层出现两处腐化，且没有测试守护测试的 docstring。
- **证据**：F08, F09, F16, F17, F26, F27, F28
- **反常识点**：测试的角色不是「验证代码正确」，而是「纪律的可执行载体 + 事故史档案」；但档案的封面（docstring 计数、路由文件描述）无人校对，恰恰在最显眼的计数上失真。
- **下次行动**：修复类提交强制「测试同步增量」；docstring 改为不列数字的表述或补元断言（→ ACT-1）；区域路由文件的描述性计数同步修正并避免硬编码数字（→ ACT-2）。

## 3. 可复用模式（E 阶段，L1-draft）

> G3 质量门：每个模式给出 ≥1 个非当前领域的迁移候选场景。V 阶段修正已并入（迁移场景标注待验证；P2 触发条件放宽）。

### P1 · 合规条规的二元分流（机器守卫 vs 文字条款）

- **触发场景**：产品/站点有一条必须遵守的内容纪律（引文版本、禁用词、合规声明、品牌用语）。
- **核心步骤**：新增纪律先做「可判定性测试」——能否写出**无误伤**的机器断言？能 → 进构建期守卫/契约测试；不能（规则自身的陈述页会被误伤）→ 进文字条款页，并在工程规范中登记「为何不自动化」。
- **本案证据**：F12（引文版本进构建硬检查）、F14（不笼统称帛书本留文字条款并登记理由）、F15（页脚分层进钩子）。
- **跨项目呼应**：/fupan/ 记载的 OKF 实践中 toctree 门禁拦下 11 处不可达断链（F36），为同一「门禁化」思路在知识包场景的复现（门禁实现位于 awesome-okf-xs，非本仓，仅作呼应证据，不足以升级成熟度）。
- **反模式**：①把不可机械判定的纪律强行自动化，误报累积后团队开始忽略所有警告；②把可判定的纪律只写进文档，靠人眼把关。
- **迁移候选场景（待验证）**：隐私政策的个人信息收集声明机器扫描；品牌 VI 禁用色值/字体的 CI 断言；开源许可证头检查。

### P2 · 止血触发器——第二次为同一错误付费起即评审根治

- **触发场景**：采用了「先凑合上线」的临时方案（手写 HTML、产物入库、手动同步），已开始产生维护成本。
- **核心步骤**：为临时方案登记「付费次数」；第二次为同一问题付费当天触发根治评审；根治验收标准是「消除根因」——废除、收窄、替换皆可，不以恢复原状或拆除守卫为目标。
- **本案证据**：F04（产物入库）→ F05/F06（两次为产物付费，±6975 行）→ F07（当天重构）；F09（词干器守卫的根治是收窄断言而非拆除）。
- **反模式**：①「等月底统一重构」——债务利息持续累积；②每次在产物上打补丁——补丁成本随产物体积增长；③根治时不补测试——同类问题换形式复发。
- **迁移候选场景（待验证）**：手动发布第二次加班 → 自动化流水线评审；复制粘贴配置第二次改漏 → 配置中心评审；手工对账第二次差错 → 自动对账评审。
